# Data Model: Employee Leave Management MVP

## Modeling conventions

- PostgreSQL UUID primary keys are generated by the application or database and exposed through REST DTOs.
- Business timestamps use `timestamptz` in UTC. Leave dates use `date` and are interpreted in the configured organization time zone.
- Leave quantities are stored as integer `units`, where `1` unit is one half-day. REST DTOs expose `days` as multiples of `0.5`.
- Mutable aggregate roots carry `version bigint`. Every concurrency-sensitive update command supplies the target aggregate's required `expectedVersion`; balance-changing commands additionally use pessimistic row locks.
- Audit and status/movement history tables are append-only. Normal master-data removal is represented by deactivation.
- Human-entered reasons and comments have explicit nonblank and length constraints. Password hashes, session identifiers, and sensitive security data never appear in audit payloads.

### Role and UserAccountRole

`Role` contains exactly the fixed authorization codes `EMPLOYEE`, `MANAGER`, and `ADMINISTRATOR`. `UserAccountRole` is a unique pair of account and role, allowing legitimate multi-role users. Every user account must have at least one role; create and update validation reject empty or duplicate role arrays and any value outside the fixed set.

An administrator creates an `EmployeeProfile` and its password-backed `UserAccount` together in one transaction. The required `initialPassword` exists only in the employee-creation transport command, is hashed before `UserAccount` persistence, and is never an entity field or response/audit property. No password-reset, invitation, SSO, magic-link, or first-login-password-change entity or workflow exists in the MVP.

|---|---|---|

| `version_number` | integer | Positive; unique per leave type |
| `effective_from` | date | Required |
| `effective_to` | date nullable | Not before `effective_from`; null means open-ended |

Policy date ranges for the same leave type must not overlap. For approved self-cancellation, calculate the cutoff as the start of `start_date - cancellation_cutoff_days` in the organization time zone; self-cancellation is allowed only before that instant. Pending requests may be cancelled before a decision.

### LeaveBalance

Current summary for an employee, leave type, and nonoverlapping policy period.

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | Primary key |
| `employee_id` | UUID | FK to employee |
| `leave_type_id` | UUID | FK to leave type |
| `period_start`, `period_end` | date | Required; end is not before start |
| `allocated_units` | integer | Nonnegative |
| `adjustment_units` | integer | Signed administrator adjustments |
| `reserved_units` | integer | Nonnegative |
| `consumed_units` | integer | Nonnegative |
| `version` | bigint | Lock/version guard |
| `created_at`, `updated_at` | timestamptz | Required |

Unique key: `(employee_id, leave_type_id, period_start, period_end)`. Periods for the same employee and leave type must not overlap.

Derived quantities:

- `entitled_units = allocated_units + adjustment_units`
- `available_units = entitled_units - reserved_units - consumed_units`

`allocated_units` is the FR-021 employee leave-balance allocation and the sole MVP allowance mechanism; there is no allowance-basis field or entity. For every balance-tracked policy, `available_units` cannot fall below zero. A tracked request creates exact reservation lines or fails atomically. An untracked policy has no request balance line.

### EmployeeTeamCalendarEntry (read projection)

This is a dedicated, non-entity projection and must not reuse a private request DTO.

| Field | Source | Rules |
|---|---|---|
| `employee_display_name` | EmployeeProfile | Only the display name |
| `start_date`, `end_date` | LeaveRequest | Leave dates only |
| `status` | LeaveRequest | Only `PENDING` or `APPROVED` |

The repository predicate is `(request.employee_id = viewer.employee_id) OR (viewer.manager_id IS NOT NULL AND request.employee.active = true AND request.employee.manager_id = viewer.manager_id)`, together with `request.status IN (PENDING, APPROVED)`. The projection never contains employee/request identifiers, leave type, duration mode, reason, balance, decision comment, status history, audit history, or other request data.

## State transitions and balance effects

| Command | Allowed current status | Result | Balance-line effect | Active slots | Authority |
|---|---|---|---|---|---|
| Submit | None | `PENDING` | For `tracks_balance=true`, create `RESERVED` lines and increment reserved units after mandatory availability validation | Insert active | Employee owner |
| Approve | `PENDING` | `APPROVED` | `RESERVED` to `CONSUMED`; decrement reserved and increment consumed | Remain active | Direct manager only; never self |
| Reject | `PENDING` | `REJECTED` | `RESERVED` to `RELEASED`; decrement reserved | Deactivate | Direct manager only; never self |
| Cancel pending | `PENDING` | `CANCELLED` | `RESERVED` to `RELEASED`; decrement reserved | Deactivate | Employee owner |
| Cancel approved | `APPROVED` and before cutoff | `CANCELLED` | `CONSUMED` to `RESTORED`; decrement consumed | Deactivate | Employee owner |
| Administrative correction: cancel pending | `PENDING` | `CANCELLED` | `RESERVED` to `RELEASED`; decrement reserved | Deactivate | Administrator only; reason required |
| Administrative correction: cancel approved | `APPROVED` | `CANCELLED` | `CONSUMED` to `RESTORED`; decrement consumed | Deactivate | Administrator only; reason required |
| Administrative correction: reopen rejected | `REJECTED` | `PENDING` | After full revalidation, `RELEASED` to `RESERVED` and increment reserved for tracked leave; append a new `RESERVE` movement | Reactivate/recreate only after overlap validation | Administrator only; reason required |

No ordinary command exits `REJECTED` or `CANCELLED`. Same-status administrative corrections and every administrative transition not listed above are forbidden, including `CANCELLED -> APPROVED`, `REJECTED -> APPROVED`, `APPROVED -> PENDING`, and `CANCELLED -> PENDING`. A failed correction changes no request, balance, ledger, occupancy, history, or audit state. Every successful transition inserts exactly one immutable status-history record and at least one matching audit event in the same transaction; prior ledger/history rows are never rewritten.

## Calculation and validation rules

1. Resolve the effective policy for each requested date and organization time zone.
2. Reject an inverted range, inactive employee/type, invalid policy period, or a half-day on a disallowed type.
3. For half-day mode, require one date and create the selected `AM` or `PM` slot.
4. For full-day mode, traverse the inclusive range. Apply configured weekly-off and holiday treatment, creating `AM` and `PM` slots for each chargeable date.
5. Reject a result with zero chargeable units.
6. Check active overlap before insert; rely on the active-slot unique index for concurrent races.
7. For every balance-tracked type, allocate units to applicable balance periods, lock balances in `(period_start, id)` order, require sufficient unreserved units, and reserve atomically. Untracked types skip balance rows and lines.
8. Return the same authoritative calculation DTO from preview and submission; submission recalculates rather than trusting client totals.

Approval repeats eligibility, policy, duration, overlap, and balance-line validation. A material policy/calculation change returns a conflict requiring the employee to submit a new request rather than silently changing approved duration.

## Command versions, transactions, and locks

| Command | Required client version | Lock/consistency strategy and single-transaction writes |
|---|---|---|
| Leave submission | None (new request) | Recalculate; lock balance rows `(period_start, id)`; validate availability/overlap; create request, reservation lines, `RESERVE` movements, slots, initial history, and audit |
| Manager approval/rejection | `LeaveRequest.version` | Authorize, lock request, compare version, repeat direct-report/self checks; lock balances; apply conversion/release, occupancy, ledger, history, and audit |
| Employee cancellation | `LeaveRequest.version` | Authorize ownership, lock request, compare version and cutoff/status; lock balances; release/restore, deactivate slots, append ledger/history/audit |
| Administrator correction | `LeaveRequest.version` | Require administrator, lock request, compare version and exact source/action; lock balances; apply the listed balance/slot effects and append ledger/history/audit |
| Employee/reporting update | `EmployeeProfile.version` | Require administrator; optimistic compare-and-increment; validate manager role/activity/self-reference; update and audit atomically |
| Leave-type update/deactivation | `LeaveType.version` | Require administrator; optimistic compare-and-increment; update and audit atomically |
| Policy-version creation | Parent `LeaveType.version` | Require administrator; lock/compare parent, validate nonoverlapping effective range, insert immutable version and audit atomically |
| Holiday update/soft deactivation | `CompanyHoliday.version` | Require administrator; optimistic compare-and-increment; set `active=false` for removal and audit without deleting historical data |
| Balance-period allocation | None (new period) | Require administrator; enforce nonoverlap/idempotency; create balance, `ALLOCATE` movement, and audit atomically |
| Balance adjustment | `LeaveBalance.version` | Require administrator; lock balance and compare version; update summary and append `ADMIN_ADJUST` movement/audit atomically |

All command transactions use Spring `REQUIRED` semantics. Any authorization, validation, stale-version, constraint, ledger, occupancy, history, or audit failure rolls back the complete command. Missing required `expectedVersion` is `400 VALIDATION_FAILED`; a mismatch is `409 STALE_VERSION` and exposes no current version or protected data. Internal line versions do not replace the command's aggregate version.

## Required indexes and constraints

- Unique indexes on normalized login, employee number, leave type code, holiday date, policy version number, and applicable idempotency keys. Holiday removal updates `active=false`; it never deletes the holiday row.
- Check constraints for date order, positive chargeable/movement units, nonnegative reserved/consumed/allocated units, cutoff days, and half-day single-date shape.
- Exclusion or equivalent constraints preventing overlapping policy versions and balance periods for the same owner/type.
- Partial unique active-slot index enforcing employee/date/AM-or-PM overlap protection.
- Request indexes on `(employee_id, submitted_at desc)`, `(employee_id, status, start_date)`, and `(status, start_date)`.
- Employee index on `manager_id` for reporting-scope queries.
- Balance index on `(employee_id, leave_type_id, period_start, period_end)`.
- Holiday index on active date; history/audit indexes on aggregate reference and descending timestamp.
- Report queries use the request status/type/date indexes and remain paginated; add specialized indexes only from measured query plans.

## Migration outline

1. `V001__identity_and_people.sql`: organization settings, accounts, roles, account roles, employees, reporting constraints and indexes.
2. `V002__leave_policy_and_calendar.sql`: leave types, effective policy versions, weekly offs, holidays and nonoverlap constraints.
3. `V003__leave_balances.sql`: balance periods, balance summaries, movements and integrity constraints.
4. `V004__leave_requests.sql`: requests, occupied slots, balance allocation lines, active-overlap constraint and query indexes.
5. `V005__history_and_audit.sql`: request status history, audit events, append-only permissions/rules and indexes.
6. Later changes use new forward migrations. Local demo reference data is isolated under a development-only Flyway location and is never enabled in production.
